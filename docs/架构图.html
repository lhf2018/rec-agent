mini-agent · 设计方案 v1.5 · 代码未落地

在合适时机主动推荐，而不是每次触发都推一把

资格回答「能不能推」，机会回答「值不值得推」，引擎给出封闭候选，Agent 只在有缺口时做受控决策与解释， 校验与交付决定「能不能给用户看」。用三臂评测证明 Agent 是否真有增益。

v1.5 评审修订 参数待确认 / 待验证 详评：架构评审-v1.5.md
总判：具备主动推荐 Agent 的基本骨架（引擎与 Agent 分离、封闭候选、独立校验、生成≠交付）， 但 v1.4 的「主动性」偏弱——更像事件触发后尝试推荐。v1.5 补上机会判断、 可编码路由与Agent 增益验收。
优点
  • 计算与决策分离
  • 硬约束不可降级绕过
  • 有基线对照意识
原最大问题
  • 缺「值不值得推」
  • 路由条件难落地
  • Agent 易变成文案层
优先只改三处
  • 机会判断
  • 可编码路由+增益定义
  • 用户状态 MVP+三臂评测
最大风险：验证机制与主动策略不足，略重于 Runtime 架构不足。先写清「何时不调模型、如何证明增益」，再写循环代码。

工具白名单

查商家/商品详情 · 对比 · 曝光历史 · 补充检索一次 · 提交。不能扫全库、改库存、发券、改画像。

可靠：底线与降级

第一版必须
  • 封闭候选 + 工具白名单
  • 硬约束失败不可输出/绕过
  • 证据过期与候选版本
  • submit 幂等；交付再验
  • 生成 ≠ 展示
降级边界
  • 可用：硬约束通过的基线子集
  • 禁止：未校验 Top3 直出
  • 禁止：降级绕过拒绝/忌口
  • 部分失败：只留通过项

多样性：引擎粗控，Guard 终裁最终名单同类目商家数（≤2 是否全场景待确认）。
